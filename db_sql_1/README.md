# pulse-platform

## Создание БД с нуля

Скрипты находятся в `db_sql`. Каждый запускается целиком через SQL-редактор
GUI-клиента (например, DBeaver). Команды psql, включение файлов и shell не нужны.
Это первоначальная установка, не миграция существующего окружения.

### Подготовка

- Подготовьте административное подключение PostgreSQL с правами суперпользователя.
- Убедитесь, что доступны расширения `pgcrypto` и `citext`.
- Создавайте отдельную пустую БД. Роли с указанными именами не должны существовать.
- В SQL-клиенте включите остановку при первой ошибке и выполнение скрипта
  в одной сессии. Не добавляйте внешнюю транзакцию к файлам с BEGIN/COMMIT.
- Версия PostgreSQL должна быть проверена в целевой среде: данный набор
  не проходил интеграционный прогон на сервере PostgreSQL.

### Роли и пароли

В `000_create_roles.sql` локально замените две заглушки паролей. Используйте
разные секреты длиной не менее 16 символов. Незаменённые заглушки запрещены.
В SQL-литералах одинарную кавычку экранируйте удвоением.
Не коммитьте заполненные секреты и учитывайте историю запросов GUI-клиента
и серверное журналирование SQL.

- `pulse_platform_owner`: NOLOGIN, владелец БД и прикладных объектов.
- `pulse_platform_app`: LOGIN, runtime-пользователь приложения.
- `pulse_platform_readonly`: LOGIN, чтение бизнес-данных без прямого доступа к auth.

Роли PostgreSQL не являются ролями приложения из `auth.roles`.
Не подключайте приложение владельцем или суперпользователем.

### Создание БД и схем

`001_create_database.sql` выполняйте отдельно с autocommit: CREATE DATABASE
не допускается внутри транзакции. После этого вручную переключите редактор
на подключение к `pulse_platform`.

Каждая схема имеет отдельный файл, содержащий её таблицы, ограничения, индексы,
представления, функции, триггеры и комментарии. Объекты создаются через
`SET LOCAL ROLE pulse_platform_owner`; при завершении транзакции роль восстанавливается.
Файлы проверяют имя целевой БД. Существующие прикладные схемы не пропускаются.

### Начальные данные

Отдельно создаются роли и разрешения, системный пользователь, источники,
каталог инцидентов, переходы статусов, площадки, зоны и подразделения.

Каталог содержит 2 группы, 2 категории и 21 пункт чек-листа.
Матрица переходов содержит 15 переходов из актуального скрипта incident.
Старый отдельный seed с 13 переходами не применяется: смешивание наборов
изменяло бы итоговую матрицу, добавляя переход REJECTED → ARCHIVED.

Системный пользователь имеет UUID `00000000-0000-0000-0000-000000000001`,
логин `__system__`, заблокированный пароль `!` и роль INTEGRATION.
Демонстрационные сотрудники и пользователи отсутствуют в основной установке.

### Права

`090_grant_permissions.sql` ограничивает PUBLIC, выдаёт приложению права на
бизнес-таблицы и последовательности. Для `audit.audit_log` приложению
разрешены SELECT и INSERT, но не UPDATE, DELETE и TRUNCATE.
Readonly получает SELECT на бизнес-таблицы и представления без прав записи.

Права по умолчанию задаются для объектов, которые в будущем создаст
`pulse_platform_owner`. DDL от runtime-пользователя не поддерживается.
Автоматическое изменение структуры приложением должно быть отключено.

### Первый администратор

В `100_create_admin.sql` заполните логин, отображаемое имя и пароль.
Скрипт отклоняет заглушки, пустые имя/логин, резервный логин и пароль
короче 16 символов или длиннее 72 байт. Создаётся пользователь с SUPERUSER.
В БД сохраняется bcrypt-хеш. Существующий логин приводит к ошибке,
пароли и назначения ролей существующих пользователей не изменяются.

### Проверка и обработка ошибок

`999_check_installation.sql` проверяет основные объекты, владельцев,
контрольные количества seed, системного пользователя, администратора и
основные эффективные права. Не вызывает nextval и не создаёт бизнес-записи.
Контрольные количества рассчитаны на новую установку: после изменения
справочников проверки могут намеренно завершаться ошибкой.
Проверки не заменяют интеграционные тесты приложения.

Каждый файл со своим BEGIN/COMMIT — отдельная транзакция, общей транзакции
на всю установку нет. При ошибке остановитесь, выполните ROLLBACK,
если клиент оставил транзакцию открытой, исправьте причину и повторите
только неуспешный шаг. Уже выполненные DDL-файлы повторять нельзя.
Создание ролей и создание БД — независимые шаги; проверяйте их состояние
при частичном сбое. Автоматического удаления БД или схем нет.

### Демонстрационные данные

`db_sql/dev` содержит необязательные файлы для изолированного локального
стенда. Не запускайте их в production. См. `db_sql/dev/README.md`.

### Действующие окружения

Этот набор нельзя запускать поверх существующей БД. Изменения работающих
окружений требуют отдельных миграций и резервного копирования.
